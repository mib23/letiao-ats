# 乐跳 ATS (内用版) 技术架构设计文档

## 〇、 架构概述

本项目采用前后端分离的架构模式，以实现灵活的模块化更迭并保障系统性能。核心技术栈基底选定为基于 `.NET 8` 的 Web 服务与基于 `Vue 3` 的现代前端框架。在数据层充分考虑内用型 ATS 频繁的复杂查询和列表展示场景，采用轻量级的高性能 ORM `Dapper` 直接操作 `MySQL` 数据库。

---

## 一、 系统技术栈选型

| 层面 | 技术栈/组件 | 理由与场景说明 |
| :--- | :--- | :--- |
| **前端展现层** | **Vue 3** (Composition API) + **Vite** | 提供更细粒度的响应式管理和极速的冷启动、热重载能力。 |
| **前端 UI 库** | **Element Plus** | 极其适合 B 端后台系统的成熟 UI 组件库，开箱即用的 Form, Table, Tree, Dialog 等满足 90% 的页面需求。 |
| **状态管理与路由** | **Pinia** + **Vue Router 4** | Vue3 官方推荐的新一代状态管理，剔除 Mutation，支持完整的 TS 类型推断；管理路由拦截与权限控制。 |
| **后端核心框架** | **.NET 8 Web API** | 微软最新长期支持(LTS)版本，自带高性能内核、极低内存占用、完善的依赖注入(DI)与异步机制。 |
| **持久层 (ORM)** | **Dapper** | 轻量级微 ORM，几乎等同于原生 ADO.NET 的性能。ATS系统有很多极其复杂的聚合查询（如“人才库+多标签+流水线状态”的复合查询），避免重型 ORM (如 EF Core) 产生的劣质 SQL。 |
| **数据库** | **MySQL 8.x** | 稳定可靠的开源关系型数据库，利用其原生的 JSON 数据类型特性（可存储那些千奇百怪、非标准化的简历解析零散数据）。 |

## 二、 后端 (.NET 8) 架构设计

后端建议采用经典的**分层架构 (N-Tier Architecture)** 或 **清洁架构 (Clean Architecture)** 思想变体来规避业务逻辑与数据访问的强耦合。

1. **API 层 (Presentation Layer / Web API)**
   - 负责控制器 (Controllers) 暴露 HTTP 接口。
   - 使用 `.NET 8` 内置的 `Swagger (Swashbuckle)` 进行 API 文档自动生成。
   - 全局拦截器与中间件设置：全局异常捕获 (Exception Handling Middleware)；全局统一的响应格式 (`{ code, msg, data }`)；JWT Token 校验拦截。

2. **业务逻辑层 (Business Logic Layer / Application)**
   - 包含系统的核心业务规则（如“简历保护期合并判断”、“防撞单校验”、“Offer 流状态控制”）。
   - 只依赖于接口，由上层通过 ASP.NET Core 的内置 DI (Dependency Injection / `IServiceCollection`) 注入进来。

3. **数据访问层 (Data Access Layer / Repository)**
   - 封装基于 `Dapper` 的数据增删改查仓储 (Repository)。
   - 使用 IDbConnection (如 `MySqlConnection`) 并行管理连接池。
   - 针对长效聚合查询编写参数化原生跨表 SQL（防范 SQL 注入）。

4. **基础设施层 (Infrastructure / Common)**
   - 第三方履历解析 API (AI 解析网关) 的网络调用封装。
   - 三方邮件/短信发送网关集成 (`MailKit`、阿里云 SMS SDK)。
   - OSS 文件存储服务的封装策略 (本地盘/跨网络通用接口抽象)。

## 三、 前端 (Vue 3) 架构规范

由于 ATS 包含大量的复杂表单交互（结构化招聘跟进、Offer审批框等），前端的目录抽象极为重要。

1. **权限与路由动态化**
   - 通过导航守卫 `router.beforeEach` 在根节点拦截本地是否存有有效 JWT Token。
   - 根据登陆后返回的角色组信息 (HR / 业务侧 / 管控侧) 动态从前端注入菜单表与挂载页面路由 (`router.addRoute`)，做到无权限页面白屏拦截。
2. **状态驱动的拖拽看板 (Kanban)**
   - 使用类似于 `vuedraggable` / `Sortable.js` 的插件基于 Vue3 制作推简看板卡片。拖拽释放的回调统一发送 Ajax 以流转后端状态。
3. **二次组件封装**
   - 为了开发效率，需基于 Element Plus 二次封装专有组件：
     - `DictSelect`: 统一字典下拉框（如民族、学历、淘汰原因等，避免硬编码）。
     - `CVPreviewDrawer`: 屏幕右侧推出的通用型简历预览抽屉组件，以便能够在“投递列表”、“人才库搜索页”等处多路复用。
4. **统一服务层 (Service)**
   - 使用 `Axios` 构建拦截器，每次请求在 Header 埋入 `Authorization: Bearer <token>`。
   - 集中响应拦截，处理 401 (过期踢回登录层)、403 (无权动作) 等公共 HTTP 异常弹窗。

## 四、 核心数据模型 (DB 物理设计关键点)

由于采用 `Dapper`，数据库的设计要求更为严谨和扁平化。几个核心表的设计要求：

- **`ats_candidate` (候选人库主表)**：人员底表，以姓名、混淆加密手机号/邮箱作为 Unique Keys 强约束；存储人才的基础画像（脱敏）。
- **`ats_job_posting` (职位表)**：管理岗位的存续、状态（发布/暂停）、职责描述要求以及预算 HC 数。
- **`ats_application_pipeline` (招聘流程表)**：**极其关键的一张表**，维系候选人和职位的多对多关系。记录一个候选人在特定职位中当下的状态（“一面”、“淘汰”）、推进时间节点与责任 HR。
- **`ats_timeline_log` (时间线轴表)**：系统和人工针对简历所有的动作统一写于此。字段包含 `关联候选人ID`, `动作类型 (系统通知/人工备注)`, `动作结果/文案`, `操作者`, `创建时间`。前端调接口全量拉取做成竖向时间轴。

## 五、 系统环境与部署拓扑

本内用系统可以支持在企业局域网或内网可信云服务器下敏捷私有化发布。

1. **反向代理与静态资源服务器**：采用 `Nginx`，对外暴露单一端口。前端 Vue 编译产物 (`dist`) 交由 Nginx 托管分发；配置 `location /api/` 进行反向代理至 `.NET 8 Kestrel` 服务器。
2. **服务承载态**：利用 `.NET 8` 的高跨平台特性，后端可被打包进轻量化 `Docker Image`，与 MySQL, Redis (视日后是否需要做高频字典缓存) 集群统一交由 `Docker Compose` 编排启动。
3. **文件挂载 (存储)**：在配置容器或服务时，必须将上传的简历原件目录隔离化映射 (`Mount`) 到宿主机独立物理磁盘上，防止容器销毁产生数据火葬场，并定期由 DBA 打包冷灾备。
