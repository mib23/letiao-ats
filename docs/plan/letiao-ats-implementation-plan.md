# 乐跳 ATS (纯内用版) 敏捷开发实施与验证计划

本文档基于《乐跳企业招聘管理系统（letiao ATS）PRD V1.3》，将产品需求拆解为分步骤、可验证的敏捷开发阶段，指导研发与测试团队有序推进实施落地。

---

## 阶段 0： 系统基建与基础公共服务 (Week 1-2)

**目标**：完成核心技术架构搭建，确保系统底座稳固，打通各端基本骨架。

| 模块 | 开发任务项 | 验收/验证标准 (Acceptance Criteria) |
| :--- | :--- | :--- |
| **0.1 基础设施搭建** | • 应用本系统的既定技术栈：前端 (Vue 3 + Element Plus)，后端 (.NET 8 Web API)，数据库 (MySQL + Dapper ORM)<br>• 初始化代码仓库 (前端脚手架、.NET 8 WebAPI 工程骨架)，配置CI/CD流水线<br>• 搭建开发/测试/生产三套 MySQL 数据库环境 | • 能够成功运行前后端 ``Hello World`` 与 Swagger API 页面<br>• 后端通过 Dapper 成功发起对 MySQL 研发数据库的探活请求<br>• 代码提交后自动触发构建过程 |
| **0.2 数据库与数据建模** | • 设计核心实体 ER 图 (用户、角色、职位、简历、候选人流程节点、操作日志)<br>• 产出与评审 DBA 建表 SQL 脚本 | • 可在数据库中查阅到完整的表结构与索引<br>• 执行初始化SQL不报错，产出 Markdown/PDF版的数据字典 |
| **0.3 账号认证与权限底座 (RBAC)** | • 接入企业扫码/单点登录 (SSO) 或基础账号密码登录机制<br>• 建立后台 RBAC 模型 (资源、角色、用户绑定)，特别是数据隔离机制 | • 测试用例：创建不同角色 (系统管理员, HR, 用人经理)，使用不同账号登录，接口防刷与页面路由拦截生效。 |
| **0.4 公共服务层抽离** | • 搭建并封装统一对象存储 (OSS) 服务，用于简历原件/头像/附件上传<br>• 搭建全局的操作日志记录模块 (供 Timeline 使用) | • Postman 测试上传接口，能成功返回文件的CDN访问URL。<br>• 发起 API 请求，可在 ``sys_log`` 表内准确记录人员操作轨迹。 |

## 阶段 1： 核心主干与资产入库 (Week 3-5)

**目标**：跑通“职位发布到简历手工入库”的核心资产流，让 HR 能够放弃本地文件夹。

| 模块 | 开发任务项 | 验收/验证标准 (Acceptance Criteria) |
| :--- | :--- | :--- |
| **1.1 基础配置与组织架构** | • 系统内实现部门树形结构管理<br>• 人员台账维护 (HR、普通员工分配) | • 系统管理员界面能顺利画出与真实企业一致的部门树，并挂载人员。 |
| **1.2 职位管理模块** | • 职位 CRUD (创建、修改、启/停封存)<br>• 职位指派负责 HR 与用人部门 | • HR 能成功新建一条“Java高级工程师”职位，保存并上架，在列表页可按状态或关键字过滤查阅。 |
| **1.3 简历上传与初级解析库** | • 提供简历单份/多份批量上传通用组件<br>• 对接/集成简历 AI 解析引擎服务 (如通过 API 或内部开源 OCR+NLP)<br>• 简历标准呈现模板视图开发 | • HR 上传一份不标准的 PDF 简历测试，系统能在 **3秒** 内落库，并成功结构化解析出：姓名、电话、学历等核心字段。<br>• 界面展示“原件预览 (左) + 结构化信息表 (右)” |
| **1.4 防撞单基础规则** | • 简历入库级查重拦截：“姓名+手机/邮箱”强校验 | • 录入重复手机号（同一库）时，前端抛出明确的 Toast 阻断提示“该候选人已存在”，强行合并/取消。 |

## 阶段 2： 看板流转与 IM 协同推进 (Week 6-8)

**目标**：实现在线协同流转，告别微信发文件，业务方能够在 IM 端轻量化审批简历。

| 模块 | 开发任务项 | 验收/验证标准 (Acceptance Criteria) |
| :--- | :--- | :--- |
| **2.1 拖拽式招聘流转看板** | • 当前职位下的投递候选人展示面板 (按状态分组：初筛、面试、背景调查等)<br>• 看板的横向拖拽扭转状态开发<br>• 异常流闭环：淘汰动作强制弹窗选理由 | • 在 UI 界面可以通过鼠标长按候选人卡片，拖进“一面”列；点击“淘汰”时必须出现下拉框选填淘汰原因。 |
| **2.2 IM卡片协同审批** | • 对接企业 IM (例如钉钉/企微) 的工作台消息下发能力<br>• 研发带交互 Button 的简历提报卡片推送服务<br>• 后端回传处理逻辑闭环 | • HR 点击“推荐业务”；<br>• 用人经理在手机企微收到卡片；<br>• 业务直接点卡片上的“通过”，看板中该候选人自动移入下一阶段。 |
| **2.3 简历保护期与公私海逻辑** | • 定义系统定时任务 (Cronjob)，扫描无动态简历并自动退回公海<br>• 库内查重防抢夺机制 | • 修改某候选人最后跟进日期为30天前，触发任务后，该候选人标记为“公有”，其他HR搜索并可添加至新岗位。 |
| **2.4 批量效率操作** | • 基于列表形式实现：批量勾选候选人，批量移动状态，批量打标签 | • 勾选 5 位候选人，点击“批量初筛淘汰” -> 5 位候选人状态并发变更完毕并写库。 |

## 阶段 3： 内外全面触达与全景档案 (Week 9-11)

**目标**：实现系统自动发通知、收集外部 H5 回执，以及构建人才全生命周期的 Timeline。

| 模块 | 开发任务项 | 验收/验证标准 (Acceptance Criteria) |
| :--- | :--- | :--- |
| **3.1 邮件短信网关与模板动态化** | • 接入短信云服务(如阿里云)及邮件网关 (SMTP)<br>• 管理平台短信/邮件模板占位符解析引擎实现 | • HR 设置 `{{姓名}}您好` 模板，系统能正确发送“张三您好”的真实短信与邮件到指定手机测试号。 |
| **3.2 外部H5回执采集** | • 轻量化短链 H5 页面开发(含接受/拒绝调期交互)<br>• 无登录状态下的安全票据交换 (Token 校验保护) | • 收到的邀约短信链接，在手机浏览器打开显示正确日程，点击“确认参加”后，系统后台候选人状态由“待确认”变更为“已确认面试”。 |
| **3.3 面试官协同与日历** | • 面试官看板界面，打分与结构化评价框<br>• 同步企业日历状态 (如果是企微/Exchange) | • 面试官在系统内可独立撰写“张三”的面评记录，打出A+并提交。 |
| **3.4 全景时间线 (Timeline)** | • 将零散存储的：系统短信下发记录、HR手工备注、流转状态变更聚合到一个按时间排序的展示组件中 | • 打开候选人详情页，一屏可阅读：昨天 10:00 HR建档 -> 11:00 推荐 -> 今天业务通过，轨迹条理清晰。 |

## 阶段 4： Offer、入职数据资产盘活 (Week 12-14)

**目标**：完善末端转化闭环，并对数据进行上层报表分析。

| 模块 | 开发任务项 | 验收/验证标准 (Acceptance Criteria) |
| :--- | :--- | :--- |
| **4.1 Offer审批与自动化闭环** | • 制定 Offer 线上审批流 (多级流程控制)<br>• Offer PDF 水印与合成下载，并带H5接收录入 | • 候选人接受 Offer H5；后端状态归档为“待入职”，流程在此圆满收口。 |
| **4.2 顶部全局复合搜索引擎** | • 引入高效检索手段 (如 ElasticSearch) <br>• 在前端 Header 顶栏提供常驻搜索框及复合筛选页 | • 搜索“五年经验 + Java + 不在北京 + 曾拿过Offer但不来”，需1秒内出准确名单结果。 |
| **4.3 看板与报表聚合** | • 单职位的全链路漏斗分析表<br>• 公司层面的 HR 效能大盘统计 | • 数据大屏展示：XX岗本周查阅300人，初筛50人，Offer2人；各个 HR 平均反馈响应时间低于要求标准飘红等。 |

## 后续建议

该计划为框架指导原则，实际实行中建议各研发小组每周 (Sprint) 组织 Demo 演示会议，强制要求演示**“可验证标准”**中的成果，以便及时应对需求在开发落地过程中的失真与偏差。
